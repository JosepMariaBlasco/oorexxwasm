ooRexx Playground

ooRexx 5.3.0 · WebAssembly runtime: loading…

Write ooRexx and press Run. This is the real ooRexx interpreter, the same C++ code as the one you install, compiled to WebAssembly and running in your browser, threads included. Standard input is interactive: when a program reads, type in the console. Your files stay in your browser: upload them (or drop them on the page, or link a folder) to run them or ::requires them. The extension classes (json.cls, rxregexp.cls, csvStream.cls…) and the Rexx Parser (Rexx.Parser.cls, which also highlights and checks the program as you type) are preloaded. There is no shell, but a program can use JavaScript and the page, as objects (.JSObject) or as commands (ADDRESS DOM, ADDRESS FETCH), and ADDRESS JDOR draws: JDOR, Rony G. Flatscher's drawing commands from BSF4ooRexx, on the browser's canvas (see the JavaScript & the page, The page, the classic way and Drawing samples).

Each run starts a fresh interpreter in its own Web Worker, and every ooRexx thread (START, early REPLY, .Alarm) is a further worker sharing its memory, so the page stays responsive and Stop always works. When a program reads standard input, its thread waits on shared memory until you send a line: PULL, LINEIN, CHARIN, TRACE ? and rexxtry work as in a terminal. Ctrl+D sends end of file.

    
Your files live in /home/rexx, the current directory of every run: what you upload or create there, and what a program writes there, is kept in this browser, on this device, until you delete it. Folders keep their structure (Folder, a dropped folder, or an uploaded .zip), so relative ::requires work; Download all gives everything back as a .zip. In Chrome and Edge, Link folder mounts a folder of your computer as /home/rexx/NAME/, read & write or read only: edit there with your own tools, run here. Click a file to edit it and Run to run it; any program can ::requires it or read it. In the console, ↑ and ↓ recall earlier lines. The console understands ANSI escape sequences for colors and styles ('1b'x || '[31m'…; see the ANSI colors sample). Sockets reach only WebSocket servers, and there is no shell, so ADDRESS commands for one fail (ADDRESS DOM, FETCH and JDOR work).

How the playground works

  

    
Running

    
Pick a sample or write your own program, then Run (Ctrl+Enter). Stop (Esc) ends it at once, endless loops included. Arguments is what PARSE ARG gets. Every run starts a fresh ooRexx interpreter (5.3.0, the real C++ code compiled to WebAssembly) in its own worker; ooRexx threads (START, early REPLY, .Alarm) are real threads too.

    
Standard input and the console

    
    
      
  • If the Standard input box is empty, input is interactive: when the program reads (PULL, LINEIN, CHARIN, TRACE ?, rexxtry), type in the console and press Enter. Ctrl+D sends end of file. ↑ and ↓ recall earlier lines.
    • 
      
  • If the box has text, that text is the whole input, followed by end of file.
    • 
      
  • Colors tell the streams apart: stdoutstderrtraceyouyou, in interactive trace. Trace goes where .traceOutput sends it (.error, unless you redirect it), but the interpreter tells the page which lines are trace (the traceback of an error included) and which are error messages, and when interactive trace is the one reading (.debugInput). Change the colors with ⚙ (Settings).
    • 
      
  • The console understands ANSI escape sequences for colors and styles ('1b'x || '[31m'…; see the ANSI colors sample); ESC[2J clears it.
    • 
    

    
The editor

    
The Rexx Parser highlights the program and checks its syntax as you type: an error is shown under the editor and its line is underlined. style picks one of the Parser's highlighting styles (auto follows the page theme); highlight turns it all off. Tab inserts two spaces. Edits to a sample are kept while the page is open.

    
Your files

    
    
      
  • Every run has /home/rexx as its current directory. Your files live there, and what a program writes there stays for the next runs. Click a file to edit it (Run then runs it); ↓ downloads it, × deletes it.
    • 
      
  • New creates a file (a path like lib/util.cls creates the folder too). Upload adds files (a .zip can be unpacked), Folder adds a whole folder with its subfolders, and you can also drop files or folders on the page. Download all gives everything back as a .zip.
    • 
      
  • These files are kept in this browser, on this device, until you delete them (Clear files).
    • 
      
  • Link folder (Chrome, Edge) mounts a folder of your computer as /home/rexx/NAME/, read & write or read only. Edit there with your own tools and run here: the folder is read again before every run and when you come back to the page. Deleting in a linked folder always asks; nothing is ever written to a read-only one. Several folders can be linked at once. Each linked folder is also in REXX_PATH, so ::requires "lib/util.cls" finds /home/rexx/NAME/lib/util.cls without the folder's name.
    • 
      
  • Any program can ::requires or read these files, with relative paths as usual.
    • 
    

    
Libraries

    
Preloaded: the extension classes (json.cls, rxregexp.cls, csvStream.cls, yaml.cls, dateparser.cls, socket.cls, streamsocket.cls, mime.cls, smtp.cls, rxftp.cls) and the Rexx Parser: ::requires "Rexx.Parser.cls", "parser/Highlighter.cls", or call highlight "-a prog.rex" and call elements "prog.rex" (see the Rexx Parser sample).

    
Drawing (JDOR)

    
ADDRESS JDOR draws: JDOR, the drawing command handler of BSF4ooRexx by Rony G. Flatscher, here on the browser's canvas. ::requires "jdor.cls" sets up the JDOR environment, an image and its window, and address jdor selects it (in each routine, as for any environment: the default one, the shell, does not exist here); call addJdorHandler "NAME" sets up another one. Then commands like newImage 300 200, color red, moveTo 10 10, fillRect 100 50, winShow draw, as documented in BSF4ooRexx's JDOR Synopsis. There is no Java here: objects that commands return say what they are (a JDOR Image (#99)), and errors read JDOR (web): .... The Drawing (JDOR) samples are Rony's, adapted to ::requires "jdor.cls" (instead of BSF4ooRexx); programs written for BSF4ooRexx also run unchanged, through this build's small BSF.CLS (just what JDOR programs use). Windows float over the page: drag them by the title bar (frameless ones anywhere), close them with × (on a frameless one it shows when the pointer is over it); they stay until the next run. loadImage and saveImage use your files; winScreenSize is the size of this page. Printing and the clipboard depend on what the browser allows.

    
JavaScript and the page

    
::requires "js.cls" gives JavaScript objects as Rexx objects. .js is the worker that runs your program (it has fetch, the browser's local database and WebSockets); .js~page is the page itself (its document, the DOM): .js~page~document~title = "Hi". Messages read properties and call methods (o~name, o~name(a, b), o~name = v); names are found whatever their case, and o["exactName"] is exact. A Promise is waited for with ~await. JavaScript cannot call Rexx back while it runs: .js~handler(object, "MESSAGE") gives a function that queues the call, and .js~eventLoop sends the messages (see Events from the page). The full reference is at the top of js.cls.

    
ADDRESS DOM (::requires "dom.cls") builds windows with commands, no objects needed: 'NEW "Sign up"' opens a floating panel, FIELD, BUTTON and TEXT fill it, and 'WAIT INTO ev' waits for the next event. ADDRESS FETCH (::requires "fetch.cls") does HTTP: "GET" url, then "JSON INTO data"; RC tells how it went. See the The page, the classic way samples, and the top of dom.cls and fetch.cls. Panels, like JDOR windows, stay until the next run.

    
Limits

    
There is no shell, so ADDRESS commands for one fail (ADDRESS DOM, FETCH and JDOR work, see above). Sockets reach only WebSocket servers, and fetch only servers that accept requests from other sites (CORS). Memory is the browser's. Recursion is less deep than natively (a browser worker has a smaller stack).

    
Privacy

    
Everything runs in your browser. Your programs and files are never sent anywhere: the page only downloads the interpreter and its libraries.
